## 项目

### [dify-rag-optimization](https://github.com/Shilin-Pro/dify-rag-optimization)

企业知识库 RAG 检索优化。根因是 PDF 切分把句子切碎（81 个分段平均只有 37 字），重建切分并改用父子分段后，同一套检索参数下 Hit@6 从 72.4% 提到 93.1%。

- 32 道题的评测集，含 4 道负样本，专门看模型会不会瞎编
- 试过但没用的也记了：纯关键词检索只有 9.4%；Rerank 提不动命中率；rerank 配阈值 0.5 会把结果全过滤掉（48.3%）
- 端到端拆过耗时：检索只占 1.2%，98.8% 在生成，所以继续抠检索没意义

### [ChatBI-Dify](https://github.com/Shilin-Pro/ChatBI-Dify)

自然语言查数助手，三个版本演进。V1 本地 4B 模型配 8900 字符 Prompt，V2 换云端模型后降到 506 字符，V3 加两条纠错回路处理用户说法和库里实际值对不上的情况。

- 早期 14 个用例 100% 通过，复查发现其中 6 个和 Prompt 示例几乎一字不差，重做留出集后掉到 70%。70% 才是真实水平
- 6 个故障的根因复盘：Code 节点误判伪装成模型生成错 SQL；直连数据库改知识库导致检索空 11 分钟；两个 LLM 节点 num_ctx 不一致让查询从 65s 降到 19s

### [excel2mysql](https://github.com/Shilin-Pro/excel2mysql)

把脏 Excel/CSV 导入 MySQL，生成带业务口径的 Schema Prompt，并检测 10 类会让 NL2SQL 写错的陷阱。

## 在 Dify 之外重写过一版（未开源）

Dify 那版跑通后，发现两件事靠工作流解决不了：插件和工作流耦合、写操作没法做权限和审计。于是用 Python 把能力层重做了一遍，下面几条是当时的设计取舍：

- **插件契约**：manifest + 统一信封 + CLI 三件套。插件只认信封，不反向依赖编排器，换 harness 不用改插件
- **三层缓存**：先试过模糊匹配，实测正确率只有 10%，改成 SQL 指纹 + 同义归一 + 数据版本号，做到零误判
- **写操作闸门**：写操作不直接执行，先出预览卡片等人确认；写模板的 WHERE 带 expect_status 乐观锁，实测两人并发只有一个成功
- **指标语义层**：8 个指标 / 8 个维度固化成可执行口径，指标类问题零 LLM 调用，热路径 61ms（原来 15.7s）
- **结果直接渲染**：查询结果 ≥2 行时不走 LLM 复述，省 3~5 秒且没有幻觉
- **上下文压缩**：小模型装不下整份表结构会编造列名，改成先用 BM25 选表再切块，提示词从 8843 压到 1753 字符，字段没丢
- **评测**：自建 200 题回归集，分覆盖、准确、拒绝三类，复杂问题多次运行的通过率从 81% 到 96.6%；黄金 SQL 全部手写，每次回归落台账

也做过一次自我审计，把 10 项技术债按危险程度排了序（HTTP 层无鉴权、DB 用 root、硬编码绝对路径这些），后来把鉴权、只读账号、配置外置补掉了。

## 做事方式

- 先定验收标准再改代码，测试集分 core / fresh 两批，防止在同一批题上过拟合
- 出问题先分解测量再判断，不猜；分得清是标准答案错还是模型错
- 用 dsh + WorkBuddy 结对写代码，架构和验收标准自己定，生成的代码逐条核对、跑完回归再用
